Reflective DLL Injection

Notes on reflective loading and the Windows PE structures involved in loading a DLL from memory.

Overview

Reflective DLL Injection (RDI) is a technique developed by Stephen Fewer. It is closely related to manual mapping, where a PE image is mapped into memory without relying on the ordinary DLL-loading path.

Under the standard Windows loading model, an application commonly uses LoadLibrary to load a DLL from a file path. Reflective loading changes this model by handling important parts of the image-loading process in memory.

Understanding the technique requires familiarity with the PE format, process structures, imports and relocations.

1. Locating API Addresses

Windows processes contain structures that describe loaded modules and their metadata. One relevant structure is the Process Environment Block (PEB), which contains information about the current process.

The PEB contains a loader-related structure commonly referred to as Ldr. This structure maintains information about modules loaded into the process.

The Thread Environment Block (TEB) provides access to the PEB. On x86 systems, the relevant TEB access convention uses the FS segment register; on x64 systems, it uses GS.

  • x86: the PEB pointer is commonly found at TEB offset 0x30.
  • x64: the PEB pointer is commonly found at TEB offset 0x60.

The loader's module lists can then be examined to understand which DLLs are present in the process and where their images are mapped.

2. Finding Exported Functions

Once the base address of a module is known, its exported functions can be examined through the Export Address Table (EAT).

The PE export information is described by IMAGE_EXPORT_DIRECTORY, which is referenced through the export entry in the PE data directory.

The export directory contains important arrays, including:

  • AddressOfFunctions: function address RVAs.
  • AddressOfNames: name RVAs for named exports.
  • AddressOfNameOrdinals: ordinal indexes corresponding to names.

A PE parser begins with the DOS header, follows the e_lfanew offset to the NT headers, and then examines the optional header and data directories to locate the export information.

3. Understanding the PE Image Layout

A PE file contains headers and sections. Sections may hold executable code, initialized data, resources or other information.

The PE headers describe both the file layout and the expected in-memory image layout. These layouts are not identical: raw file offsets and relative virtual addresses (RVAs) have different meanings.

Sections

The section table is described by IMAGE_SECTION_HEADER. Relevant fields include:

  • VirtualAddress: the section's RVA in the image.
  • PointerToRawData: the section's file offset.
  • SizeOfRawData: the size of the section's data in the file.
  • VirtualSize: the section's expected size in memory.

4. Import Address Table

The Import Address Table (IAT) contains the addresses of functions imported from other modules. The import directory is represented by an array of IMAGE_IMPORT_DESCRIPTOR structures.

Three fields are particularly relevant:

  • OriginalFirstThunk: points to import lookup information.
  • Name: identifies the imported module.
  • FirstThunk: identifies the IAT entries.

Import entries may identify functions by name or ordinal. The loader resolves these references and updates the IAT with addresses that the image can use at runtime.

5. Base Relocations

A PE image may not always be mapped at its preferred image base. When the actual base differs from the preferred base, relocation information is needed to adjust absolute addresses embedded in the image.

The .reloc section contains relocation data. The relocation directory describes blocks of relocation entries. The loader uses the difference between the actual and preferred image bases, often called the relocation delta, to determine how addresses must be adjusted.

This is why understanding the relocation directory and relocation types is important when studying PE loading.

6. Execution and Initialization

Mapping an image is not the same as completing all of its initialization. A Windows image has additional runtime expectations, including correct memory protections, resolved imports, relocation handling and initialization routines.

For reverse engineering, these details are useful when identifying manually mapped modules and understanding why their memory layout may differ from conventionally loaded DLLs.

Key Structures

  • PEB — process environment information.
  • TEB — thread environment information.
  • PEB_LDR_DATA — loader data and module lists.
  • IMAGE_DOS_HEADER — DOS header.
  • IMAGE_NT_HEADERS — PE signature and headers.
  • IMAGE_SECTION_HEADER — section metadata.
  • IMAGE_EXPORT_DIRECTORY — exported function metadata.
  • IMAGE_IMPORT_DESCRIPTOR — imported module metadata.
  • IMAGE_BASE_RELOCATION — relocation block metadata.
